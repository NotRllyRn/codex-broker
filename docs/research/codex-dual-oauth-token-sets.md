# Research: Dual OAuth credential sets from Codex headless/device-code login

## Summary

**Qualified yes:** Codex 0.145.0 has no client-side rule preventing the same ChatGPT user from completing two separate login grants, and each completed grant returns a token bundle. To retain both bundles, the logins must use **different `CODEX_HOME` values / credential-store keys** (normally separate Codex/app-server processes); a second completed login in the same home saves one replacement `AuthDotJson` and overwrites the previous local credential bundle. However, OpenAI's public source and auth documentation do **not** promise that two refresh tokens issued to the same user/client are separate revocation families or that revoking one cannot affect the other, so “independent and independently revocable” must not be treated as a supported guarantee without an OpenAI-auth-service test or confirmation.

## Findings

1. **High — Two complete login transactions can produce two credential responses, but codes are not tokens.** In 0.145.0's device-code path, Codex first receives a `device_auth_id`, one-time `user_code`, polling interval, and verification URL. Polling `/deviceauth/token` later returns an **authorization code** plus PKCE challenge/verifier; Codex then exchanges that authorization code at `/oauth/token` for an ID token, access token, and refresh token. The device/user codes and authorization code are short-lived transaction artifacts—not bearer access credentials and not renewable refresh credentials—and Codex does not persist them. This is consistent with RFC 8628's separation of device/user codes from the eventual access-token response and RFC 6749's authorization-code exchange model. Repeating the whole authorization transaction while signing in as the same user is not rejected by any Codex client check. [Codex 0.145.0 `device_code_auth.rs`](https://github.com/openai/codex/blob/rust-v0.145.0/codex-rs/login/src/device_code_auth.rs) · [Codex 0.145.0 `server.rs`](https://github.com/openai/codex/blob/rust-v0.145.0/codex-rs/login/src/server.rs) · [RFC 8628](https://datatracker.ietf.org/doc/html/rfc8628) · [RFC 6749](https://datatracker.ietf.org/doc/html/rfc6749)

2. **High — A single app-server permits only one pending account login at a time.** `AccountRequestProcessor` stores one `Option<ActiveLogin>`. Starting browser or device-code login removes/drops the existing active attempt, which cancels it, then installs the new attempt. Thus, do not launch two simultaneous device-code requests through one app-server and expect both to finish. Complete them sequentially, or use separate processes/homes. A completed first login followed by a second is permitted; only pending-login concurrency is suppressed. [Codex 0.145.0 `account_processor.rs`](https://github.com/openai/codex/blob/rust-v0.145.0/codex-rs/app-server/src/request_processors/account_processor.rs)

3. **High — Same-home login overwrites the locally active bundle; Codex does not maintain an account/token-set list.** `persist_tokens_async` constructs one `AuthDotJson` containing `auth_mode`, optional API key, one `TokenData` (`id_token`, `access_token`, `refresh_token`, `account_id`), `last_refresh`, and other optional auth fields, then calls `save_auth`. File storage opens `$CODEX_HOME/auth.json` with `truncate(true)`; keyring storage uses a single key derived from canonical `CODEX_HOME`; ephemeral storage performs one map `insert` for that home. Therefore a second successful login in the same home replaces—not appends to—the first credential object. Current OpenAI docs likewise describe one cached login shared by CLI and extension and located in `auth.json` or the OS credential store. [Codex 0.145.0 `server.rs`](https://github.com/openai/codex/blob/rust-v0.145.0/codex-rs/login/src/server.rs) · [Codex 0.145.0 `storage.rs`](https://github.com/openai/codex/blob/rust-v0.145.0/codex-rs/login/src/auth/storage.rs) · [OpenAI Codex authentication](https://developers.openai.com/codex/auth)

4. **Concrete safe layout for retaining two candidate sets.** Use two private homes, for example `CODEX_HOME=/secure/codex-a` and `CODEX_HOME=/secure/codex-b`, configure file or keyring storage separately, and run one complete `codex login --device-auth` (or the 0.145.0 app-server `account/login/start` device-code variant) in each. Sign into the same ChatGPT user/workspace in both browser approvals. Each process then reads/refreshes only its own stored bundle. With app-server, wait for the `account/login/completed` notification before considering that home's bundle durable. **Do not create “two sets” by copying one `auth.json`: that produces two copies of the same refresh token, not two grants.** [Codex 0.145.0 `account_processor.rs`](https://github.com/openai/codex/blob/rust-v0.145.0/codex-rs/app-server/src/request_processors/account_processor.rs) · [OpenAI CI/CD auth guidance](https://developers.openai.com/codex/auth/ci-cd-auth)

5. **High — Refresh tokens are rotated in practice, and each stored bundle must have a single serialized writer.** Codex posts `grant_type=refresh_token`, `client_id`, and the current refresh token. The response can contain replacement ID/access/refresh tokens; `persist_tokens` replaces every returned field and preserves a field only when omitted. Version 0.145.0 explicitly classifies `refresh_token_reused` as exhausted and tells the user the refresh token “was already used,” which is direct client evidence of one-time rotation/replay detection. OpenAI's CI/CD guidance accordingly requires one `auth.json` per runner or serialized workflow and warns that another machine can rotate the token first. RFC 9700 requires public-client refresh tokens to use rotation or sender constraint and explains rotation's replay-detection purpose. [Codex 0.145.0 `manager.rs`](https://github.com/openai/codex/blob/rust-v0.145.0/codex-rs/login/src/auth/manager.rs) · [OpenAI CI/CD auth guidance](https://developers.openai.com/codex/auth/ci-cd-auth) · [RFC 9700 §2.2.2/§4.14](https://datatracker.ietf.org/doc/html/rfc9700)

6. **High — Separate logins are not publicly guaranteed to be independently revocable.** On logout, Codex 0.145.0 best-effort posts the currently stored refresh token (or access token only if no refresh token exists) to `https://auth.openai.com/oauth/revoke`, then deletes local credentials even if revocation fails. This targets only the bundle visible in that home at logout. But RFC 7009 explicitly leaves cascading policy to the authorization server: revoking a refresh token may revoke related access tokens and the underlying grant. Neither the pinned source nor OpenAI Codex auth docs specify whether two same-user/same-client logins receive distinct grant/token-family identifiers, whether a new login invalidates an older family, or whether revoking one family leaves the other valid. Consequently, two returned refresh-token strings are **candidate separate sets**, not a contractual independence boundary. [Codex 0.145.0 `revoke.rs`](https://github.com/openai/codex/blob/rust-v0.145.0/codex-rs/login/src/auth/revoke.rs) · [Codex 0.145.0 `manager.rs`](https://github.com/openai/codex/blob/rust-v0.145.0/codex-rs/login/src/auth/manager.rs) · [RFC 7009 §2.1](https://datatracker.ietf.org/doc/html/rfc7009#section-2.1)

7. **Medium — OpenAI's session UI is not evidence of per-Codex-CLI revocation.** OpenAI documents multiple active first-party sessions and individual/all-session logout, but explicitly says the Active sessions page does **not** show Codex CLI sessions. Therefore that UI cannot be relied on to enumerate or individually revoke these two CLI refresh-token sets. “Log out all” may have broad effects, but the published page does not define its exact relationship to Codex CLI OAuth refresh-token families. [OpenAI: Managing active sessions](https://help.openai.com/en/articles/20001257-managing-active-sessions-in-chatgpt) · [OpenAI: Log out all devices](https://help.openai.com/en/articles/9243857-how-do-i-log-out-of-all-of-my-devices)

8. **High — Security and operational caveats.** File-backed `auth.json` is plaintext secret material (although created mode `0600` on Unix) and contains access and refresh tokens; prefer OS keyring where available, keep each home private, never commit/log/copy it casually, and treat it like a password. Device codes invite remote-phishing/social-engineering risk: approve only a flow initiated on the intended machine, as both Codex's prompt and RFC 8628 warn. Use TLS for any nonlocal app-server transport and authenticate it. Workspace restrictions can reject a completed exchange if the ID token's workspace does not match configured allowed IDs. Finally, access tokens are short-lived bearer credentials; refresh tokens are longer-lived credentials used to obtain new access tokens; an ID token conveys identity claims and is not interchangeable with either. [OpenAI Codex authentication](https://developers.openai.com/codex/auth) · [Codex 0.145.0 `device_code_auth.rs`](https://github.com/openai/codex/blob/rust-v0.145.0/codex-rs/login/src/device_code_auth.rs) · [RFC 8628 §5](https://datatracker.ietf.org/doc/html/rfc8628#section-5) · [RFC 6749 §§1.4–1.5](https://datatracker.ietf.org/doc/html/rfc6749#section-1.4) · [OpenAI Codex app-server](https://developers.openai.com/codex/app-server)

## Bottom line

- **Can the same user log in twice?** The Codex client permits two completed transactions; yes, this can yield two returned token bundles.
- **How retain both?** Complete each transaction under a distinct `CODEX_HOME`/credential-store key (prefer separate processes). A single app-server cannot keep two pending login attempts concurrently.
- **Does login #2 overwrite `auth.json`?** Yes, when both use the same file-backed home; keyring/ephemeral storage is likewise one record per home.
- **Are copied bundles independent?** No. Copies share one rotating refresh token and will race.
- **Are separately obtained bundles independently refreshable/revocable?** Possibly, but **not verified or guaranteed by published OpenAI primary sources**. Rotation within each bundle is evidenced; cross-grant invalidation/revocation semantics are undocumented.

## Gaps

OpenAI publishes no primary-source contract for same-user/same-client **cross-login refresh-token family semantics**. A definitive answer on independence requires a controlled live test: create two homes via two separately approved logins, record only cryptographic hashes of each refresh token to establish distinctness, refresh A then B, revoke A via Codex logout, and verify B can still refresh—without exposing tokens. Even that demonstrates current behavior, not a durability guarantee; product-critical reliance should be confirmed with OpenAI Support or a documented supported integration. No live account login or token handling was performed for this research.
