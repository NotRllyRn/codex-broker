# Managed credential checkpointing

## Decision

Windowkeeper will keep one mutable `ACTIVE` credential lineage and one immutable, externally owned `EXPORT` snapshot per account.

- OAuth enrollment durably captures the source credential, advances `ACTIVE` through one managed refresh, and attempts one separate export refresh.
- Existing `EXPORT` rows are never refreshed, replaced, or used by Windowkeeper. Reauthentication advances only `ACTIVE`; it creates an export only when the account has none.
- Normal usage, activation, and reconciliation use only `ACTIVE` and checkpoint opaque `auth.json` after every authenticated runtime, including RPC failure and cancellation.
- Export remains protected and downloadable, but is documented as an enrollment snapshot with no upstream guarantee of independent renewability.
- Named exports and credential leasing are deferred. OpenAI exposes no supported credential-cloning contract, so Windowkeeper will not claim multiple static downloads are independent.
- New manual-token enrollment is retired. Historical enum/database values remain readable.

This export-preserving interpretation supersedes the portions of the supplied plan that remove `EXPORT`, its route, UI, and rows.

## Upstream evidence

Pinned Codex `rust-v0.145.0` establishes that:

- `account/read` returns `account: Option<Account>` and ChatGPT `email: Option<String>`.
- `account/read` with `refreshToken=true` requests a real proactive refresh.
- Codex owns ordinary refresh timing and persists successful rotations through its credential store.
- refresh-token reuse/expiry/revocation can be permanent; duplicate refreshable lineages are not guaranteed.
- `forced_chatgpt_workspace_id` is a scalar configuration restriction.
- app-server uses newline-delimited JSON-RPC; error codes are numeric and useful auth reasons may be in bounded message/data text.

## Invariants

1. Exactly one `ACTIVE` row exists for an authenticated account; old generations become `RETIRED` only in the same transaction that inserts their replacement.
2. At most one `EXPORT` exists. Once created, its bytes and bundle id do not change during reauth, usage, activation, reconciliation, or failure handling.
3. No normal operation calls `account/read` with `refreshToken=true`.
4. Every authenticated runtime is fresh, serialized by the account credential lock, quiesced, captured, and checkpointed before plaintext deletion.
5. RPC success, failure, and cancellation all checkpoint first. A checkpoint failure quarantines the runtime root and prevents semantic success.
6. Vault payloads treat `auth.json` as opaque bytes. New captures exclude `config.toml`; legacy config is validated but never restored.
7. Runtime configuration is generated by Windowkeeper for every runtime, including the optional forced workspace restriction.
8. A credential mutation followed by RPC failure still advances `ACTIVE` while preserving the RPC error.
9. Login authentication becomes durable before usage is attempted. Initial usage is a separate operation.
10. Account `null` means authentication required; nullable email remains valid; identity type must be `chatgpt`.

## Milestones

### 1. Foundations

- Restrict new vault captures to `auth.json`, add fingerprinting, and ignore legacy stored config during materialization.
- Replace runtime reuse/idle release with fresh runtime, existing-runtime lookup, discard, and quarantine primitives.
- Generate canonical `config.toml` every time.
- Make transport EOF fail pending RPCs and wake notification consumers; improve bounded auth-error classification.
- Add migration 006 for current login states while preserving ACTIVE, EXPORT, RETIRED, and historical methods.

### 2. Managed operations

- Add atomic ACTIVE promotion and a single cancellation-safe `_run_managed` helper.
- Route usage refresh through it and separate usage persistence from credential persistence.
- Preserve specific failure codes and open a checkpoint incident on quarantine.
- Route activation and startup reconciliation through the same helper without changing ambiguity/idempotency rules.

### 3. Enrollment and export

- Make login own the credential lock for its full runtime lifecycle.
- Capture/promote OAuth source immediately, create the managed branch, then attempt export once without risking ACTIVE rollback.
- Keep existing EXPORT immutable on reauthentication.
- Commit login before scheduling initial usage.
- Cancel only the existing login runtime.
- Remove manual-token UI and reject new manual-token attempts while retaining historical values.

### 4. Verification and documentation

- Update fake Codex to the exact account shape and add credential-mutation/error/EOF markers.
- Replace tests that require routine two-way forks with ACTIVE-checkpoint and immutable-EXPORT assertions.
- Add the mandatory rotate-then-RPC-fail regression.
- Update product, operations, security, context, and release documentation.

## Validation contract

Required automated evidence:

- nullable email accepted; `account=null` requires authentication; mismatched email rejected;
- new payload captures only auth; legacy config cannot override generated policy;
- workspace constraint appears in generated config;
- fresh runtime cannot silently reuse old credential state;
- clean stdout EOF yields `CODEX_TRANSPORT_CLOSED`; stderr EOF is harmless; notification wait terminates;
- normal RPCs never send `refreshToken=true`;
- usage, activation, and reconciliation credential mutations advance ACTIVE and leave EXPORT unchanged;
- credential rotation followed by RPC failure still persists the new ACTIVE generation;
- checkpoint failure does not report success and preserves the runtime root;
- migration 006 preserves existing ACTIVE/EXPORT rows;
- manual-token creation/reauth is unavailable;
- complete Ruff, formatting, mypy, Pyright, and pytest gates pass.

Protected live-account verification remains required for the unsupported enrollment fork behavior and export usefulness.
